# Screen Studio 轨迹与视频对齐调研

日期：2026-09-11。范围限于两个本地 Screen Studio 样本的只读分析；未修改其项目、未复制视频或光标素材到本项目、未开发业务代码。

## 结论

对这两个**单段区域录制**样本，可以把鼠标事件的 `processTimeMs` 减去同一 display session 的 `processTimeStartMs`，得到以原始 MP4 PTS=0 为起点的源视频时间（秒）。鼠标坐标是带录制区域偏移的显示器逻辑坐标；映射到 MP4 应先减 `bounds.x/y`，再按 MP4 实际宽高缩放。两个样本恰好是每个逻辑坐标 2 个 MP4 像素。

第一阶段应以 MP4 实测尺寸和 session `bounds` 计算比例，不能硬编码 2、不能以 `recordingScale` 推算，也不能使用数组下标或名义 FPS 推算事件时间。原视频为可变帧率（VFR），渲染时必须按视频 PTS 取帧。

## 证据与计算结果

分析对象：

- `~/Screen Studio Projects/Area 2026-09-11 00:19:01.screenstudio/`
- `~/Screen Studio Projects/Area 2026-09-11 01:08:34.screenstudio/`

以下表中的 MP4 属性由 macOS AVFoundation 读取，并用本机已有的 Bilibili 私有 `ffmpeg` 做**只读核验**；该私有二进制不属于本项目依赖，不会作为产品运行依赖或被分发。

| 样本 | display `bounds`（逻辑坐标） | MP4 实际编码尺寸 | 元数据时长 | MP4 PTS 时长 | 结论 |
| --- | --- | --- | ---: | ---: | --- |
| 00:19:01 | `(13, 152, 1387, 645)` | `2774 × 1290` | 19.799710 s | 19.802 s | `2774/1387 = 1290/645 = 2` |
| 01:08:34 | `(13, 152, 1387, 645)` | `2774 × 1290` | 9.520459 s | 9.522 s | 两个轴同为 2 |

事实：两份 `polyrecorder.log` 都记录了 `displayScaleFactor: 2`、`recordingScale: 0.5`、SCStream `sourceRect:(13,152,1387,645) width:2774 height:1290`。实际 MP4 尺寸与 AVFoundation 读取结果相同。

推断：当前样本的逻辑显示器坐标被以 Retina 2 倍写入 MP4。`recordingScale: 0.5` 没有直接令最终 MP4 变为逻辑尺寸，因此它不能替代按实际 MP4 尺寸计算的映射。

## 坐标映射与热点

事实：`metadata.json` 的 `cropRect` 与 display session `bounds` 一致，且 `cropRect.yAxis` 为 `topBasedIncreasingDownwards`。两个样本中移动和点击事件的坐标均落在该区域内；例如第一个样本移动事件范围是 `x=485.047…1039.516`、`y=180.277…761.902`，均在 `x=13…1400`、`y=152…797` 内。

建议的源视频映射（以每段真实 MP4 `W × H` 为准）：

```text
sx = W / bounds.width
sy = H / bounds.height
videoX = (event.x - bounds.x) * sx
videoY = (event.y - bounds.y) * sy
```

当前两份样本可简化为：

```text
videoX = (event.x - 13) * 2
videoY = (event.y - 152) * 2
```

计算例（00:19:01 的首个按下）：事件为 `(1035.7578125, 382.30859375)`，相对视频时间为 `4.442136834 s`，映射为 `(2045.515625, 460.617188)` MP4 像素。

事实：`cursors.json` 为每个 `cursorId` 提供 `standardSize` 与 `hotSpot`；观察到的 `arrow` 为 `standardSize=(28,40)`、`hotSpot=(5,5)`，`pointingHand` 为 `(32,32)`、`(13,8)`。

渲染语义推断/建议：若事件坐标表示用户实际指向的位置，绘制时应将它作为最终光标热点位置，而不能作为图像左上角。热点位移须随实际绘制尺寸一起缩放：

```text
imageScaleX = renderedCursorWidth  / cursorBaseWidth
imageScaleY = renderedCursorHeight / cursorBaseHeight
drawLeft = videoX - hotSpot.x * imageScaleX
drawTop  = videoY - hotSpot.y * imageScaleY
```

若以 `standardSize` 为基准尺寸，且渲染尺寸设为 `standardSize * sx/sy`，上式才化简为 `drawLeft = videoX - hotSpot.x * sx`、`drawTop = videoY - hotSpot.y * sy`。额外的 cursor-size 设置也必须同时作用于素材尺寸和热点位移。

风险：保存的 PNG 像素尺寸并不统一地等于 `standardSize` 的某个固定倍率：样本 `arrow.png` 是 `280×400`，`pointingHand.png` 是 `64×64`，两者均为 72 DPI。`project.json` 还含 `cursorSet: macos-tahoe`、`cursorSize: 1.5` 和“低分辨率时使用默认光标”设置。由此可知，轨迹文件足以定位热点，却不足以单独复刻商业应用的最终光标样式与尺寸。第一阶段应使用自有/授权明确的光标资源，按定义的逻辑尺寸缩放，并保留 `cursorId` 和热点字段；不应直接把这些 PNG 的原始像素尺寸当作渲染尺寸。

## 时间对齐

事实：同一录制段的 input 和 display session 起点几乎相同。

| 样本 | display `processTimeStartMs` | input 起点与 display 起点的差 | 首个移动相对时刻 | 末个移动相对时刻 |
| --- | ---: | ---: | ---: | ---: |
| 00:19:01 | 802.406458 | < 0.000001 ms | 78.568 ms | 19599.156 ms |
| 01:08:34 | 991.387000 | < 0.000001 ms | 428.152 ms | 9321.899 ms |

两个事件文件中 `unixTimeMs - processTimeMs` 在各自样本内的波动小于 0.001 ms，进一步说明事件共用该时间基准。AVFoundation 读取的两个视频首 PTS 都为 `0`。元数据时长与容器时长仅相差约 2.29 ms 和 1.54 ms；最后一次 mouseUp 分别仍在录制结束前约 52.72 ms 与 60.22 ms。

因此，对于本次样本，源视频时间为：

```text
sourceTimeSeconds = (event.processTimeMs - displaySession.processTimeStartMs) / 1000
```

不要以首个鼠标事件为零点。那会使第一份样本整体提前约 78.6 ms，第二份提前约 428.2 ms。

### 帧率限制

事实：MP4 容器的名义帧率分别为约 12.878 和 25.731；日志所述采集最小帧间隔为 1/60 秒。只读 `ffmpeg` 的 `vfrdet` 结果为 `VFR:0.433071 (110/144)` 与 `VFR:0.430328 (105/139)`，证明两段均非恒定帧率素材。

结论：`显示器 60 Hz`、`minFrameDuration=1/60` 和 MP4 `nominalFrameRate` 都不能用于由帧号反推事件时间。读取原视频时按解码帧 PTS 选择轨迹状态；若输出恒定帧率，则对每个输出时间点在事件时间轴插值。

## 原录制、事件与项目编辑时间线

事实：两个 `project.json` 的 `scenes[0].slices[0]` 目前都是 `sourceStartMs=0`、`sourceEndMs=录制元数据时长`、`timeScale=1`。在这一特定状态下，`zoomRanges` 的项目时间可与源视频毫秒时间对应：

| 样本 | 项目 zoomRange | 是否在对应源时长内 |
| --- | --- | --- |
| 00:19:01 | 4142–10609 ms | 是，源时长 19799.710 ms |
| 01:08:34 | 1473–8720 ms | 是，源时长 9520.459 ms |

推断：当前项目尚未裁剪或变速，所以这三种时间在数值上对齐：事件相对时间、原 MP4 PTS、项目 zoomRange 时间。

待验证/限制：一旦发生裁剪、多 slice、暂停恢复、倍速或项目导出时间线编辑，项目播放时间可能不再等于源 MP4 时间。第一阶段仅需接受自定义 `session.json` 的显式缩放区间；它应明确该区间使用的时间基准。无需兼容完整的 Screen Studio `project.json` 编辑结构。

## 有限视觉核验与未决项

通过 AVFoundation 在临时目录解码了 00:19:01 样本约 4.442 s 处的画面，得到的是不含光标的原始 Bilibili 浏览器画面，未将该帧写入本项目。解码器返回的最近帧 PTS 是约 4.222 s；这反映了该源素材的帧保持/非等间隔取帧，并非空间映射错误的证据。由于原 MP4 不含后期叠加的光标，且画面不是带已知坐标靶标的受控样例，仍无法从该帧量化热点叠加的像素误差。

因此，下列项目仍不能写成已验证事实：

- 渲染后光标热点与实际 UI 命中点的逐帧误差；应在本项目的合成样例中加入已知坐标靶标测试。
- 多显示器、负坐标、不同 Retina 倍率、非区域录制和多段录制的映射。
- 原始素材有裁剪/变速时从项目编辑时间回映射到源 PTS 的规则。
- `activeModifiers` 非空、其他鼠标按钮、自定义光标及拖拽的完整语义。

## 第一阶段可采用的边界

1. 只支持单段、未裁剪、未变速的源 MP4 与一组移动/点击事件。
2. 在 `session.json` 明确提供视频、事件文件、`bounds`、`processTimeStartMs` 与“缩放区间以源视频毫秒计”的约定。
3. 始终由真实 MP4 `W/H` 和 `bounds` 计算映射，按 PTS 解码；输出前把事件轨迹按输出时间采样和插值。
4. 光标资源与 Screen Studio 素材分离；鼠标文件保留 `cursorId`，第一阶段可将未支持 ID 回退为自有的默认光标，同时记录告警。
