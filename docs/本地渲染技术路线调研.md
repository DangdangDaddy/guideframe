# 本地渲染技术路线调研

日期：2026-09-11。状态：调研结论，尚未安装依赖、编写渲染器或执行编码性能测试。

## 范围与结论

第一阶段只实现本地 CLI：输入不含光标的 MP4、沿用 Screen Studio 字段的鼠标移动/按下/抬起事件，以及显式缩放区间；输出带平滑光标、点击反馈和缩放效果的 MP4、短 GIF、指定时间 PNG。桌面 UI、录制、点击自动生成缩放区间、云端服务、登录和遥测均不进入本阶段。

建议采用一条共享的逐帧渲染核心，三种导出都调用 `render(t, source_frame)`，避免 MP4、GIF、PNG 各自解释时间线。首阶段的简洁职责分配是：

| 组件 | 建议职责 | 首阶段定位 |
| --- | --- | --- |
| Python | JSON 校验、事件归一化、轨迹/点击/缩放状态计算、任务编排、错误与原子写入 | 主控层 |
| PyAV | 读取容器和视频流、按帧 PTS 解码、向 Pillow/NumPy 转换 | 视频输入与时间戳层 |
| Pillow + NumPy | 裁剪/缩放、RGBA 光标热点合成、点击圆环、输出 PNG | 首版画面合成层 |
| FFmpeg/ffprobe | H.264 MP4 编码与音轨封装、GIF 调色板编码、输入/输出媒体验收 | 固定版本的媒体工具 |
| OpenCV | 仅当真实基准证明 Pillow 缩放或合成不达标时，替换热点路径 | 暂不作为必需依赖 |

这条路线保留 PyAV 的逐帧 PTS 可见性，又让 FFmpeg 负责其更成熟的编码、封装和 GIF 调色板。若后续发现 PyAV 与单独 FFmpeg 带来过多重复依赖，可做一个“仅 FFmpeg 解码为 CFR 原始帧”的替代验证；它会增加原始 RGB 管道流量，不建议在没有基准数据前直接改用。

### 四类库的比较

#### PyAV

**官方事实**：PyAV 直接暴露 FFmpeg 的容器、流、包和帧。其文档明确区分 `time_base`，解码帧的显示时间是 `pts * time_base`；流声明的平均帧率、基准帧率和猜测帧率不保证准确，官方建议能用原始时间戳时优先使用时间戳。`VideoFrame` 可转换为 Pillow 图像或 NumPy 数组。官方也给出 remux 示例，说明不转码复制媒体包可避免再次有损压缩。[时间模型](https://pyav.org/docs/stable/api/time.html)；[流与帧率](https://pyav.org/docs/stable/api/stream.html)；[视频帧转换](https://pyav.org/docs/stable/api/video.html)；[remux 示例](https://pyav.org/docs/stable/cookbook/basics.html)

**项目判断**：它比 `cv2.VideoCapture` 更适合承担输入 PTS、流起点和逐帧解码。首阶段不让 PyAV同时负责全部编码和音轨封装，可减少包时间基转换、编码器构建差异和音视频交错代码。

**限制**：本机没有 PyAV。当前 `stable` 页面标示为 9.0.2，不能据此直接指定 2026 年的依赖版本。实现前需选定受支持的 Python/macOS arm64 组合，下载并锁定对应 wheel，再做离线安装和编码器能力验证。官方说明二进制 wheel 会链接 FFmpeg，因此它与单独 FFmpeg 可执行文件会增加包体和版本面。[安装说明](https://pyav.org/docs/stable/overview/installation.html)

#### OpenCV

**官方事实**：`VideoCapture`/`VideoWriter` 的实际行为取决于所用后端；官方提醒属性经过 VideoCapture→后端→操作系统/驱动等多层后可能出现不同结果。`VideoWriter` 写入固定尺寸图像帧，通常期待 BGR；接口不承担本项目的音轨封装。OpenCV 提供 `INTER_LINEAR`、`INTER_CUBIC`、`INTER_AREA`、`INTER_LANCZOS4` 等缩放算法。[VideoCapture](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html)；[VideoWriter](https://docs.opencv.org/4.x/dd/d9e/classcv_1_1VideoWriter.html)；[几何变换](https://docs.opencv.org/4.x/da/d54/group__imgproc__transform.html)

**项目判断**：不使用 OpenCV 读写视频，以免把 PTS、后端、FourCC 和音轨问题藏在便捷 API 后面。若基准显示 Pillow 的全帧缩放是瓶颈，可只引入 `cv2.resize`/局部绘制，并明确 RGB↔BGR 边界。

**限制**：本机没有 OpenCV，所谓“更快”尚未在目标机上测量。

#### Pillow

**官方事实**：Pillow 支持图像裁剪/缩放、Lanczos 等重采样、RGBA alpha composite、椭圆/圆环绘制和 PNG/GIF 写入。[Image](https://pillow.readthedocs.io/en/stable/reference/Image.html)；[ImageDraw](https://pillow.readthedocs.io/en/stable/reference/ImageDraw.html)；[图像格式](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html)

**项目判断**：其 API 足以构成首版正确性基线：光标素材统一转 RGBA，根据热点贴图；点击反馈用透明圆环；缩放时先裁源帧再恢复到输出尺寸；PNG 由最终合成帧直接保存。视频编码和最终 GIF 量化不交给 Pillow，以免一套帧时长/调色板逻辑与 FFmpeg 并存。

**限制**：每帧都做全尺寸 Lanczos 和多次图像/数组转换可能很慢；本机只有“可导入”的证据，没有性能证据。

#### FFmpeg 与 ffprobe

**官方事实**：FFmpeg 的 `fps` 滤镜会按目标恒定帧率丢弃或复制帧；`-fps_mode cfr` 同样明确表示生成 CFR。`-map ...?` 可以把缺失音轨设为可选。`palettegen` 为整段视频生成调色板，`paletteuse` 使用调色板并支持多种抖动和差分矩形模式。ffprobe 可按流/帧输出 JSON 及指定字段；MP4 `+faststart` 会把索引移到文件开头，便于播放。[FFmpeg 主文档](https://ffmpeg.org/ffmpeg.html)；[滤镜文档](https://ffmpeg.org/ffmpeg-filters.html)；[ffprobe](https://ffmpeg.org/ffprobe.html)；[格式与 faststart](https://ffmpeg.org/ffmpeg-formats.html)

**项目判断**：交付时固定项目自己的 FFmpeg/ffprobe 版本和构建配置；不搜索、借用其他应用的二进制。FFmpeg 负责 H.264/AAC 或音轨复制、MP4 封装和 GIF 调色板；ffprobe 负责可机器读取的验收证据。软件编码与 VideoToolbox 硬件编码均须实际比较后再选默认。

**许可边界**：FFmpeg 官方说明基础许可为 LGPL，但启用 GPL 组件时整个 FFmpeg 构建受 GPL 约束，并特别点名 libx264。个人本地使用、内部发放和公开分发的要求不同；打包前必须根据实际分发方式确定构建、许可证文本和对应源码提供方式。这是待决定的分发事项，不是本轮的编码结论。[FFmpeg 法律说明](https://ffmpeg.org/legal.html)

## 时间戳与帧采样方案

### 单一时间轴

所有内部时间使用秒的有理数或足够精确的十进制表示，JSON 边界再转换，避免累计浮点步进误差。

输入视频帧的归一时间：

```text
source_time_i = (frame_pts_i - first_video_pts) * video_time_base
```

鼠标事件仍按已有轨迹调研结论转换：

```text
event_time = (processTimeMs - processTimeStartMs) / 1000
```

不要把首个鼠标事件归零，也不要用数组下标、`avg_frame_rate` 或显示器刷新率推算事件时间。

### 输出采用 CFR，但动画不受输入 VFR 停顿影响

**项目建议**：MP4 首阶段固定输出 CFR。输出时刻由目标帧率生成：

```text
t_n = n / output_fps,  0 <= t_n < video_duration
```

对每个 `t_n`：

1. 输入画面选择 `source_time_i <= t_n` 的最后一帧，保持到下一输入 PTS；
2. 光标插值、点击反馈和缩放状态都直接在 `t_n` 求值；
3. 再调用同一个 `render(t_n, source_frame)`。

因此，即使 VFR 输入在静止画面上数秒没有新帧，源画面只是保持，光标和缩放仍会在每个输出 tick 更新。这里“输入 PTS 决定源画面”和“输出 CFR 时间决定动画”是两层规则，不冲突。

首阶段建议要求输入解码帧具有可用、非递减 PTS；缺失或严重乱序时明确失败，不默默按帧号补时间。视频总时长优先取可靠的呈现区间；末帧 duration 缺失时的回退规则需要在实现规格中固定并用样例覆盖。输出帧率不要从 `r_frame_rate` 盲猜：可由 session 显式指定，或采用一个由规格固定的默认值。

### PNG 时间语义

指定时间 PNG 必须从原始输入按同一源帧选择规则调用 `render(requested_time, source_frame)`，包含该时刻的缩放、点击反馈和光标，不能用 FFmpeg 从未合成的原 MP4 截帧。请求时间超出 `[0, video_duration)` 应报错；若请求时间不在 MP4 的 CFR 网格上，PNG仍按请求的精确时间求动画状态。

### GIF 时间片与调色板

建议把 GIF 时间片定义成半开区间 `[start, end)`：

```text
t_n = start + n / gif_fps,  且 t_n < end
```

每个 GIF 帧也由同一 `render(t_n, source_frame)` 生成。先完成时间裁剪、目标尺寸和帧率，再基于这批“最终渲染帧”运行 `palettegen`，随后用相同帧序列运行 `paletteuse`；不能用原视频或整段视频的颜色生成调色板。短 GIF 可以接受两次确定性重渲染，避免把所有 RGB 帧留在内存，也避免从有损 MP4 二次取帧。GIF 最终帧显示时长通常会量化到百分之一秒，任意 `gif_fps` 未必能精确表示；必须验收编码后的逐帧时长和总时长，不能只核对输入参数。`stats_mode=full/diff`、抖动方式和 `diff_mode=rectangle` 需用 UI 录屏样例比较文件大小、文字边缘和涟漪渐变后由规格确定，不把官方默认值当成本项目最佳值。GIF 无音轨。

## 音轨策略

**项目建议：输入存在音轨时默认保留，输入无音轨时正常导出静音 MP4。** CLI 可提供显式 `--no-audio`，但默认不应无提示丢弃讲解声。

时间规则：视频首帧归一为 `t=0`，音频保留其相对于原视频首 PTS 的偏移。音频早于视频的部分裁到 `t=0`；音频晚开始则保留对应的起始空段/偏移。最终容器以原视频呈现区间为基准，裁掉超出视频结束的音频；音频较短时不应使用 `-shortest` 截断视频。FFmpeg 官方说明 `-shortest` 会在最短输出流结束时停止，因此不能作为默认同步方案。

编码选择：

- 原音频为 MP4 可直接封装的 AAC、采样参数正常、时间戳无需滤镜修正时，优先 stream copy，避免再次有损编码。
- 其他音频编码、需要裁剪/偏移修正、或 stream copy 封装验证失败时，转为 AAC；尽量保持原采样率和声道数，码率默认值在样例听测后确定。
- 首阶段只处理第一个视频流和至多第一个音频流；多音轨、字幕、章节和数据流明确提示未保留。

copy 与 AAC 回退必须出现在日志和结果清单中。导出完成后用 ffprobe 核验音频编码、起点、时长和相对视频偏移，不能仅凭 FFmpeg 退出码宣称“原音轨已保留”。

## 坐标、缩放、尺寸与图层

实际解码视频尺寸 `W×H` 是画面尺寸真值；session 声明尺寸用于校验，冲突时失败，不静默缩放事件。录制区域坐标按已有调研公式映射到视频坐标。缩放倍率 `z(t) >= 1` 时，围绕目标点取得约 `W/z × H/z` 的视口，视口越界时整体平移回画面内，再恢复到 `W×H`。

建议图层顺序为：源画面缩放 → 把事件点应用同一镜头变换 → 点击涟漪 → 光标。光标热点而非左上角对准变换后的事件点。光标尺寸是否随镜头缩放由规格阶段确定；首版倾向保持输出像素尺寸稳定，以免放大时光标变得过大。首阶段建议在 JSON 校验时拒绝相互重叠的显式缩放区间并定位到冲突项，暂不引入组合或优先级规则；这是调研建议，并非用户已批准的规格。

MP4 默认保持输入显示尺寸和 1:1 像素比例。为了 `yuv420p` 兼容性，首阶段建议只接受偶数宽高；奇数尺寸直接给出可操作错误，比静默裁切或补边更容易保持坐标语义。是否未来自动补边列为待决定项。

## 色彩与像素格式

输入探测至少记录 `pix_fmt`、位深、`color_range`、`color_space`、`color_transfer`、`color_primaries` 和 sample aspect ratio。首阶段建议把支持范围限定为 8-bit SDR、方形像素、无旋转的屏幕录制：解码时按明确的输入矩阵/范围转 RGB(A) 合成，编码为 H.264 `yuv420p`，并写出与转换一致的色彩标签。

若输入标签缺失，不能假装已经“保留原色”。建议默认按 BT.709 SDR 处理并输出醒目警告和结果清单；这一默认需要用黑白阶、灰阶和彩色 UI 补丁样例确认。PQ/HLG、10-bit、广色域、隔行、旋转或非方形像素首阶段应明确拒绝，避免无提示的色调映射、位深丢失或坐标错位。是否允许缺失标签继续处理、以及默认全范围/有限范围，应由实现规格固定。

软件编码建议先以 `libx264 + yuv420p + CRF + preset + faststart` 建立可重复的质量基线；具体 CRF/preset 不在调研阶段冒充已验证默认值。VideoToolbox 只作为性能选项：本机那份 FFmpeg 4.4 确认暴露 `h264_videotoolbox`，但未编码、未测速度和画质，也不能证明未来项目构建包含它。

## 离线依赖与写入方案

完全离线应是运行时属性，也包括可重复安装：

1. 选定项目 Python 版本并创建项目虚拟环境，不依赖 `/usr/bin/python3` 的全局包。
2. 为目标平台准备锁定版本和哈希的离线 wheelhouse；只放所需的 PyAV、Pillow、NumPy，OpenCV 未通过性能门槛前不加入。
3. 提供同一来源、同一版本/构建配置的项目 FFmpeg 与 ffprobe，记录 SHA-256、许可证和构建信息；不依赖 Homebrew、PATH 或其他 App。
4. 运行时只接受本地普通文件路径，拒绝 `http://`、`https://` 等 URL 输入；FFmpeg 调用只开放必要的本地文件/pipe 协议。程序中不加入更新检查、崩溃上传、遥测 SDK 或网络请求。
5. 所有输出先写同目录临时文件，成功完成媒体探测后再原子改名；输入只读。失败/中断清理临时文件，不留下看似成功的目标文件。

FFmpeg/PyAV 的网络协议能力本身不等于发生联网；“无上传”的保证来自输入协议白名单、没有网络代码和断网端到端验收。

## 性能与资源风险

本轮没有跑真实编码，以下是风险和算术估计，不是本机性能结论：

- 1920×1080 `rgb24` 单帧约 6.2 MB，60 fps 原始帧流量约 373 MB/s；4K/60 约 1.49 GB/s。若通过多个进程管道并反复复制，带宽和内存分配会迅速成为瓶颈。
- 每帧全画面 Lanczos 缩放很可能比光标/圆环局部合成更贵；无缩放时应跳过重采样，光标素材按尺寸缓存。
- PyAV→Pillow→NumPy 的反复转换会复制像素。实现时应固定一种内部 RGB 表示，测出转换次数和峰值 RSS，再决定是否用 OpenCV 替换缩放热点。
- 若以 8 GB 作为示例内存预算，缓存整段 GIF 帧会造成明显风险；采用两次流式渲染或受控临时无损文件，内存保持为少数帧。这里的 8 GB 只是保守预算示例，不是本机内存核验结果。
- 软件 H.264 的画质可控但可能慢；硬件 H.264 可能快，但码率/画质/跨构建一致性需实测。官方或理论能力不能替代目标机基准。
- 解码、渲染、编码是串行流水线的三个阶段。队列应有上限并支持背压，不能按视频长度无限缓存帧。

首个性能基准建议使用 30 秒、1920×1080、60 fps、同时含移动光标/点击/缩放/音频的合成样例，记录总耗时、各阶段耗时、平均/最低处理 fps、峰值 RSS、输出大小和编码器。实时倍数和峰值内存阈值由规格阶段确定；没有阈值时只报告实测数据，不能宣称性能达标。

## 第一阶段可执行验收建议

1. **时间与 VFR**：构造输入画面只在已知 PTS 改变的 VFR 样例，导出 CFR；逐帧确认源画面采用 `latest source PTS <= t`，同时光标在输入静止间隔仍每个输出 tick 平滑移动。
2. **轨迹**：事件间隔包含亚毫秒、长停顿、同位置切换 `cursorId`、首事件晚于视频起点；点击时光标命中原始点击位置，不能被平滑曲线带偏。
3. **坐标与镜头**：覆盖非零录制区域偏移、热点偏移、画面四角目标、缩放进入/停留/退出边界和越界夹取；在每个边界前后抽帧检查连续性。
4. **PNG**：选择进入缩放、点击峰值、退出缩放三个时间，使用独立计算的预期像素/几何位置核对；PNG 必须含完整合成效果。越界时间明确失败且不产生文件。
5. **GIF**：给定 `[start,end)` 和 `gif_fps`，核对首末帧时刻、帧数、逐帧编码时长、最终总时长、尺寸、循环设置、无音轨、颜色数不超过 GIF 限制；调色板只从该时间片最终渲染帧生成，并确认百分之一秒时长量化后的误差符合规格。
6. **MP4**：用 ffprobe JSON 核验单视频流、目标 H.264 像素格式、尺寸、CFR、时长和色彩标签；播放器实测 Safari/Chrome/QuickTime 的可播放性。
7. **音频**：分别测试无音频、AAC 可 copy、必须转 AAC、音频晚起和音频尾部更长。用已知时刻的声学脉冲与画面标记核对 A/V 偏差，建议容差不超过一个输出视频帧；视频不能因短音轨被截断。
8. **颜色**：用黑白阶、灰阶和高饱和 UI 色块核对 RGB 往返，确保黑白不因 full/limited range 选择而压扁；缺失标签和 HDR 输入走预定警告/拒绝路径。
9. **资源**：上述 30 秒 1080p60 样例记录耗时和峰值 RSS；再用长静止段确认内存不随帧数持续增长。规格尚未设定阈值时只提交实测值，不声称性能达标。
10. **离线与安全写入**：在断网、空缓存环境从离线依赖包安装并完成三种导出；监测不到外连。导出前后比较输入 SHA-256；模拟 FFmpeg 失败和中断，目标文件不存在或保持旧版本，临时文件被清理。

## 规格阶段待固定项

1. MP4 `output_fps` 是否必须显式填写；若允许默认，默认 30、60 还是从已验证输入时间戳推导。
2. 输入色彩标签缺失时默认按 BT.709 的具体 range 处理，还是直接拒绝；HDR/广色域何时支持。
3. 光标尺寸、点击圆环宽度是否随镜头倍率变化；首阶段建议重叠的显式缩放区间直接校验失败，不定义优先级。
4. 奇数尺寸是首阶段拒绝，还是补边到偶数并在结果清单记录；本报告建议先拒绝。
5. 音频 AAC 回退的默认码率；是否只保留第一音轨；本报告建议首阶段只保留第一音轨。
6. 软件 `libx264` 与 `h264_videotoolbox` 的默认选择，以及项目实际分发方式对应的 FFmpeg 构建和许可义务。
7. 可接受的处理速度、峰值内存、GIF 最大时长/尺寸/fps 及时间量化误差。没有这些阈值时不能判断是否需要 OpenCV，也不能声称性能达标。
8. PyAV、FFmpeg、Python 的最终锁定版本。当前本机仅有其他 App 私有的旧 FFmpeg 和未锁定的系统 Python，不构成实施环境。
